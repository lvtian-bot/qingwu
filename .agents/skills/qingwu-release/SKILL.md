# 青梧版本发布

此 Skill 是青梧的发布操作说明。发布由 `v*` 标签触发 `.github/workflows/release.yml`；普通分支推送只触发质量检查。执行前核对当前工作流与 `package.json`，不要把这里的步骤当成外部平台的实时状态。

## 确定发布范围与版本

1. 检查 `git status`、本地与远端 `master` 的差异、`package.json` 与 `package-lock.json` 的版本，以及 `docs/TODO.md` 中本次已完成的事项。
2. 工作区存在未提交改动时，逐项列出每处改动（所在文件、内容摘要、可否发布的判断），交用户逐项决定提交或排除；不得以「进行中」为由默认排除，未经逐项确认不得发布。确认结果与版本号一并取得用户同意。
3. 按 `AGENTS.md` 的版本规则计算拟用版本号，向用户说明版本号、本次范围、需要改动的文件及发布后果，取得针对该版本的明确同意。未取得同意时，不修改任何版本字段，不创建、移动或删除标签，也不发布。
4. 确认本次发布对应的提交与版本标签尚未被其他发布使用；如远端已有同名标签或 Release，先核实差异，不覆盖。

## 制作并触发发布

1. 将 `docs/TODO.md` 中属于本次版本且已勾选的事项移入 `docs/TODO-ARCHIVE.md` 的 `## vX.Y.Z（YYYY-MM-DD）` 小节；未完成事项留在原处。
2. 同步更新 `package.json`、`package-lock.json` 的版本，检查两处一致；`CHANGELOG.md` 由发布工作流中的 git-cliff 生成，不手工编辑。
3. 运行 `npm run check`。本次改动涉及桌面交互时验证对应界面；涉及 DSH 引擎时验证青梧界面、DeepSeek 界面与命令执行。失败或无法验证的部分须查明并说明，不能仅凭构建通过宣布可发布。
4. 仅提交本次版本变更，提交主题为 `chore: release vX.Y.Z`。推送 `master` 并确认 Quality 工作流通过，再创建与包版本一致、指向该发布提交的 `vX.Y.Z` 标签并推送。推送标签会启动对外发布。

## 核对发布结果

1. 跟踪 Release 工作流直到结束；确认 GitHub Release 与拟用版本一致，发布说明已生成，且包含 `.exe`、`.exe.blockmap`、`latest.yml`。仅有成功日志而缺少产物不算完成。
2. 检查远端 `latest.yml` 指向实际安装包，下载入口可访问；必要时对安装包执行 HEAD 或 Range 请求，核对文件大小与返回状态。确认工作流从远端 `master` 生成并提交 `CHANGELOG.md`，没有因非快进而失败。
3. 核对远端提交、标签、Release 和本地工作区状态；明确报告版本号、工作流与产物链接、更新元数据和 CHANGELOG 状态，以及未验证的运行行为。若任何一环失败，先排查并修复；不得把仅有标签或工作流启动视为发布完成。
