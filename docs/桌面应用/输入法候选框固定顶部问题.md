# Windows 中文输入法候选框固定在顶部/左上角问题调查

> 所属模块：[桌面应用](桌面应用.md)  
> 责任范围：窗口生命周期、双界面（`WebContentsView`）焦点管理、Windows 原生输入法（TSF/IMM32）适配

## 1. 问题现象与影响

- **触发场景**：应用冷启动启动后，在青梧界面输入框中进行中文输入。
- **用户可见后果**：输入法（如微软拼音、搜狗输入法等）的拼音编码与候选词浮窗固定在窗口最顶部/左上角（(0, 0) 附近），无法跟随输入光标移动，严重遮挡标题栏与菜单。
- **临时规避手段**：点击右上角关闭按钮（最小化到系统托盘），然后在任务栏托盘区重新点击青梧图标唤醒窗口，输入法候选框即恢复正常光标跟随。
- **当前状态**：**未解决**（仅在 `ready-to-show` 补 `this.focus()` 或简单监听事件未彻底解决，需要系统性排查与验证）。

---

## 2. 核心机制与底层原理

在 Windows 系统中，中文/日文等输入法的候选框定位依赖宿主程序向系统 TSF（Text Services Framework）或 IMM32 接口实时通报光标（Caret/Selection）在屏幕上的绝对矩形位置（`ImmSetCompositionWindow` / `ITfContextView::GetTextExt`）。

当发生以下情况时，输入法因无法获取或映射有效的光标坐标，会退化到窗口客户区默认的原点坐标 `(0, 0)`：
1. **多视图焦点竞争**：同一个顶层窗口中存在多个 `WebContents`，后台视图抢占了 TSF 输入上下文。
2. **操作系统原生激活与渲染焦点脱节**：窗口在后台静默创建（`show: false`），首次呈现给操作系统时，未完成完整的 Windows 消息链（`WM_ACTIVATE`、`WM_SETFOCUS`）与 Chromium 渲染焦点绑定。
3. **坐标映射未就绪**：无边框窗口（`titleBarStyle: 'hidden'`）或最大化状态下，Chromium 的坐标系转换矩阵在首帧输入时尚未刷新。

## 3. 日志证据与关键时间线

排查本地诊断日志 `C:\Users\chile\AppData\Roaming\qingwu\logs\app.log`（2026-09-24 启动记录），发现了核心的时序差异：

```text
[23:49:28.416] [INFO] [Diagnostics] 青梧界面 WebContents 已创建: id=1, type=window
[23:49:28.417] [INFO] [Diagnostics] DeepSeek 界面 WebContents 已创建: id=2, type=window
[23:49:28.424] [INFO] [Window] 界面模式: native
[23:49:28.609] [INFO] [Diagnostics] 青梧界面 页面加载完成: pid=32972, url=file:///index.html
[23:49:29.125] [INFO] [Diagnostics] DeepSeek 界面 页面加载完成: pid=35152, url=http://127.0.0.1:3080/
```

- **关键时序**：
  - `28.609s`：青梧前台界面（id=1）加载完毕，触发 `ready-to-show` 并显示窗口；
  - `29.125s`（约 500ms 后）：后台静默预加载的 DeepSeek 官方界面（id=2, `WebContentsView`）才加载完毕。
- **后台抢焦机制**：
  DeepSeek 官方 Web 端（dsh web）挂载时会自动聚焦其聊天输入框（autofocus）。虽然该 `WebContentsView` 处于视觉隐藏状态（`setVisible(false)`），但由于它通过 `win.contentView.addChildView(dshView)` 挂载在同一个顶层窗口的视图树上，Chromium 可能在后台页面 autofocus 时将输入法 TSF 上下文切换到了后台视图上。

## 4. 为什么“关到托盘再点开”能恢复？

对比两处代码路径：
1. **冷启动阶段**：
   - 窗口以 `show: false` 启动，异步并行加载前台与后台两套 WebContents；
   - 前台先渲染完毕显示窗口，随后后台页面加载完成并触发潜在的聚焦竞争。
2. **托盘唤醒阶段**：
   - 此时后台的 DeepSeek 页面早已加载完成并稳定，不再有异步脚本抢焦；
   - 托盘点击显式调用 `windowManager.focus()`：
     ```ts
     this.mainWindow.focus();              // 触发 Windows HWND 原生激活 (WM_ACTIVATE)
     this.getTargetWebContents()?.focus();  // 确凿指定前台青梧界面 WebContents 获焦
     ```
   - 焦点被强行夺回并固定在前台界面，输入法上下文与前台输入框光标建立起正确通信。

## 5. 后续排查与拟解决方向

后续处理该任务时，应重点从以下几个方向进行验证和攻关：

1. **方向一：后台视图物理挂载隔离（推荐优先验证）**
   - 当前在 `createWindow` 时直接执行了 `win.contentView.addChildView(dshView)`。
   - 改造为：在 `native` 模式下**不把 `dshView` 挂入 `contentView`**（或直接延迟到用户切换至官方界面时再挂载/加载），避免后台视图在无边框窗口内干扰 Windows TSF 上下文。
   - 切换到官方界面时调用 `addChildView`，切回自研界面时调用 `removeChildView`。
   - **技术约束**：需注意保持 `docs/桌面应用/桌面应用.md` 中关于 WebContentsView 尺寸塌陷的约束（切换时必须显式调用 `updateViewBounds()`）。

2. **方向二：输入框获取焦点时的原生焦点确认**
   - 在渲染层输入框（`Composer.tsx` 中的 `textarea`）获得 DOM focus 或点击时，通过 IPC 向主进程通知，主进程确认当前前台 WebContents 及窗口具有完全的 Windows 输入焦点。

3. **方向三：窗口首显后模拟完整的激活流程**
   - 排查 Electron / Chromium 在 Windows 11 下无边框窗口（`titleBarStyle: 'hidden'`）首次显示时的焦点缺陷，验证是否需要微延迟执行原生窗口激活。

---

## 6. 验证标准

1. 彻底退出应用（托盘完全退出），冷启动双击打开。
2. 窗口打开后，不进行任何托盘最小化/还原操作，直接在输入框打字。
3. 中文输入法（微软拼音/搜狗输入法等）候选框必须**严格跟随光标位置**，不得出现在左上角或顶部。
4. 切换到 DeepSeek 官方界面再切换回青梧界面，候选框跟随依然正常。
