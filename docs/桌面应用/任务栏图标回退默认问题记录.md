# Windows 任务栏图标回退 Electron 默认图标问题记录

## 当前结论

- 修复状态：已恢复统一的 AppUserModelId；生产窗口图标由可执行文件内嵌资源提供，开发模式保留显式图标。现行约束见 [桌面应用](桌面应用.md)。
- 验证范围：历史修复记录包含 91 项测试、类型检查及构建通过；2026-10-24 核对当前源码，身份注册与生产窗口图标处理仍符合该方案。本次未新增安装版界面实测。
- 遗留事项：旧版本固定项可能需要取消后重新固定，处理边界见下方现行方案。本文未记录覆盖所有启动入口和升级场景的实测结果，不据此承诺永不复发。

以下现象、触发环境及临时规避操作描述修复前状态，历史方案不替代当前模块说明。

## 历史现象描述

Windows 安装版（打包后运行的客户端）在任务栏或启动后，应用图标未显示正式的蓝底白色梧桐叶品牌图标，而是回退显示为 Electron 框架底层的默认原子轨道图标（黑灰底色、浅色环绕原子核）。该问题在版本更迭与重新安装后出现过两次，属于易复发缺陷。

## 历史已知事实与触发环境

1. **界面内正常，仅系统层异常**：青梧窗口自定义标题栏左上角、关于页面等前端渲染区域图标正常显示（渲染层使用 Base64 图片直接加载），说明品牌图标素材本身完好，异常仅发生在 Windows 操作系统级（任务栏、窗口类、Alt+Tab 切换等 Win32 系统层）。
2. **无需固定到任务栏即可稳定触发**：
   - 经实机验证，**该问题无需将应用固定到任务栏**；用户即使从未固定应用，从开始菜单或桌面快捷方式直接打开青梧，任务栏上动态弹出的正在运行的窗口图标，也会直接显示为 Electron 默认原子图标。
   - 属于**第二次重复出现**：此前曾通过手动删除某个图标/图片缓存文件恢复过一次，但本次版本更迭或重新安装后再次复发，证实属于代码与打包机制层面的确定性缺陷，而非偶发固定项污染。
3. **打包产物中的图标路径缺陷（核心根因）**：
   - 目前 `package.json` 的 `build.files` 将 `build/icon.ico` 打包入 `app.asar` 归档内，但未在 `extraResources` 中提供外部物理图标。
   - `src/main/window.ts` 中的 `getIconPath()` 在生产环境中命中了 `path.join(app.getAppPath(), "build", "icon.ico")`（即 `resources/app.asar/build/icon.ico`）。虽然 Electron Hook 的 Node.js `fs.existsSync` 返回 `true`，但 Windows Win32 原生 API（`WM_SETICON`、`LoadImageW`）无法解析 `app.asar` 归档内部路径，导致窗口启动时未能成功将真实图标句柄注入操作系统。
4. **AppUserModelId 与系统图标缓存机制**：
   - 应用在启动时显式调用了 `app.setAppUserModelId("com.qingwu.desktop")`。
   - 当窗口未向操作系统正确注入原生图标句柄时，Windows 任务栏会根据该 `AppUserModelId` 尝试从系统图标缓存（`IconCache.db` / `iconcache_*.db`）匹配已知图标；若缓存记录了旧默认图标或匹配失败，Windows 就会强制回退显示框架底层默认的原子图标。此前删除缓存能临时起效，正是因为强行清空了 Windows 对该 AppId 的错误历史记录，但因代码依然无法向原生层提供物理图标，新缓存建立时极易再次退回默认图标。

## 历史临时规避操作（用户侧）

在未固定任务栏的情况下，若运行窗口依然显示默认原子图标，此前生效的临时缓解方案是清理 Windows 系统图标缓存：

1. **彻底退出应用**：关闭窗口，并在右下角系统托盘菜单中彻底点击「退出」青梧。
2. **清理 Windows 图标缓存**：
   - 按快捷键 `Win + R` 打开运行窗口，输入 `%localappdata%` 并回车；
   - 在文件夹中找到隐藏文件 `IconCache.db`（需开启“显示隐藏文件”），直接将其删除；
   - 或按 `Ctrl + Shift + Esc` 打开任务管理器，找到「Windows 资源管理器」，右键选择「重新启动」。
3. **重新打开应用**：重新从开始菜单或桌面快捷方式打开青梧，Windows 会重新生成图标缓存。
*(注：临时删除缓存只能维持当次，若底层代码未将物理图标注入 Win32 原生层，后续安装或系统刷新时仍会复发。)*

## 历史排查复盘与误区修正

### 1. 历史补丁复盘与过度修正反思
- **原子图标根因回顾（2026-09-27）**：此前窗口创建时尝试从 `resources/app.asar/build/icon.ico` 读取图标，Win32 原生层无法解析 asar 路径导致句柄缺失，系统回退到 Electron 默认原子图标。
- **2026-10-09 的过度修正及其副作用**：在引入 PE 内嵌图标后，曾误将 `app.setAppUserModelId` 当作导致图标回退的诱因予以移除。移除后虽然独立窗口可读取 PE 图标，但带来了新的严重副作用——**任务栏双图标且无法合并**：
  - Windows 任务栏窗口合并与快捷方式固定完全依赖 `System.AppUserModel.ID`（AUMID）。
  - 安装程序（NSIS）生成的快捷方式带有 `com.qingwu.desktop` 标识；移除主进程调用后，运行中的窗口缺少显式 AUMID，Windows 判定其为不同程序，导致从快捷方式启动或固定到任务栏后，活动窗口另起一个图标，无法合并。
  - 用户即便手动取消旧固定并重新固定活动图标，一旦从桌面、开始菜单或跨版本升级后启动，双图标现象仍会偶发复发。

## 现行修复方案

成熟 Windows 桌面应用兼顾“图标正常显示”与“任务栏固定合并”的行业标准实践如下：

1. **主进程显式注册统一的 `AppUserModelId`**：
   - 在 `src/main/index.ts` 启动时显式调用 `app.setAppUserModelId(CONFIG.appId || "com.qingwu.desktop")`；
   - 保持 `src/main/config.ts` 中的 `CONFIG.appId` 与 `package.json` 中的 `build.appId` 完全一致（单元测试严格断言保序）；
   - 保证 Windows 安装包快捷方式、任务栏固定项与运行中窗口三者的系统身份完全对齐。
2. **窗口主图标交由可执行文件 PE 原生接管**：
   - 由打包工具（electron-builder）在编译期将 `build/icon.ico` 写入 `qingwu.exe` 的 PE 资源段；
   - 生产环境（`app.isPackaged` 为 true）创建 `BrowserWindow` 时不传 `icon` 亦不调用 `win.setIcon`，避免 asar 路径解析失败；开发调试模式（`!app.isPackaged`）传入开发图标；
   - 系统托盘与桌面通知保留内部资源正常加载。
3. **打包配置纯净无冗余**：
   - 不在 `extraResources` 中进行非标准的外置图标解包，发布目录保持规范。
4. **存量用户的平滑过渡与恢复说明**：
   - 成熟 Windows 应用不对系统 Shell 目录（`User Pinned\TaskBar`）中的用户固定快捷方式进行静默反向修改，以保持系统纯净并避免触发安全与权限问题；
   - 针对在历史版本（如 v0.2.8）未显式设置 AUMID 期间手动将活动窗口固定到任务栏的历史用户，升级后若任务栏仍留有旧的独立固定项，仅需进行一次性操作：右键取消旧固定图标，并重新将新版青梧固定到任务栏（或从桌面/开始菜单固定）；
   - 验证应覆盖任务栏、桌面、开始菜单启动及版本升级后的图标与分组；未实测的组合不作为已经验证的结论。
