## Bug 修复

- [ ] 运行中提交的消息在青梧界面无任何可见反馈：输入框按 Enter 提交时走 `session/prompt` 的 `mode: "queue"`，引擎把消息放进 inbox 的 `next-turn` 队列，只有当前轮结束、下一步把队列项领走时才写入 `user/message` 日志；而青梧界面只订阅 `$events` / `workspace/follow` / `session/follow` 三条流并只折叠日志事件，既没有本地「发送中／排队中」回显，也没有队列区，所以提交后消息从界面上消失（实际未丢失，当前轮结束后会按原顺序出现）。修复方向：用现有 `session/follow` 流里的 `agent/inbox/spliced` 事件（或订阅 `session/control`）折出队列项，补齐乐观回显 + 队列区，并对齐官方的编辑／删除／插话操作（`session/updateQueue` 的 `edit` / `remove` / `steer`）；同时评估运行中非空草稿的发送入口（当前运行中发送按钮固定为「停止」，只能靠 Enter 触发排队）与引擎重启后队列项不会自动投递（需再发一条消息才被一起领走）的兜底
- [ ] 切换到正在运行的会话时右下角没有「停止」按钮（输入框为空时连「发送」也一并隐藏）：引擎的 `api-session/status` 只在 running↔idle 跳变时发出，切换会话、断线重连、attach 都不会重放，而切换会话时界面无条件把运行态置为 false，于是进入一个正在跑的会话后界面以为它空闲，composer 渲染的是被 `.native-send.empty { visibility: hidden }` 隐藏的发送按钮，右下角看起来整块空掉（侧栏此时仍按 `session/list` 的 running 位显示运行小圆点，两处不一致）。修复方向：切换会话时用 `session/list` 已返回的 `SessionSummary.running` 播种运行态，重连与列表刷新同样作为兜底对账，并确认运行中会话的停止入口始终可达
- [ ] 输入框草稿不分会话：`input` 是全局单份状态，切换会话既不清空也不按会话保存，在会话 A 输入的文字会原样留在会话 B 的输入框里，回车即发到 B。修复方向：按会话保存/恢复草稿（对齐官方逐会话草稿），或至少在切换时清空并提示
- [ ] 提问卡片选择不可用且设计不达标：卡片选项全部渲染在同一行小按钮里（`.native-card-actions` 为单行 flex），选项多或文案长时挤在一起难以辨识；点击回答后卡片既不消失也没有「已提交」状态（`handleQuestion` 未清理本地状态，宿主只向其他客户端推 `cancel` 帧），重复点击被宿主静默忽略，用户因此认为「选不中」，只能切官方界面回答。需按官方口径重做：纵向选项列表（label + description）、选中态与提交态、`multiSelect` 多选确认、自由文本（`custom`）、`intent: plan-review` 意图识别；实现时一并核实回执的 `clientId` 是否可能取到空串（`$events` ready 帧之前到达的瀑布帧会存 `""`，此时回执被宿主拒绝且无任何提示）
- [x] 新建会话落在「无问候语、正文全空」的会话页：点「新会话」时 `createSessionIn` 会立即在宿主建出（或复用）一个空白会话并 `setCurrentId`，而引导页（居中问候 + 居中输入框）的渲染条件只看 `!currentId`，于是用户看到顶栏只有工作区名、正文一片空白、输入框贴底的页面——其他产品在第一条消息发出前都停留在新会话引导页。修复：引导页条件改为「未选中会话，或当前会话仍为 blank、无任何消息事件且未在运行」，发出第一条消息后自然切换为会话态 ✅ 2026-09-11
- [ ] 不断弹出终端窗口（v0.0.7 已修问题的回归）：Agent 每执行一条命令就新开一个可见控制台窗口，部分控制台进程还不随命令退出（本机实测：连续三条命令三个不同 HWND 且 `IsWindowVisible=True`；上午 8:09–8:11 的 conhost 10 小时后仍存活）。**真实机制（已用对照实验定位，并否证了「windowsHide 破坏控制台继承」的旧假设）**：Electron 是 GUI 子系统程序，而 **GUI 进程不会附加到父进程的控制台**；`harness.ts` 用 `process.execPath`（electron.exe + `ELECTRON_RUN_AS_NODE`）启动引擎，dsh 又用 `process.execPath` 逐层派生 Windows Job runner 与 windows-acl runner，这几层全是 GUI 进程，于是整条链都没有控制台，直到 pwsh（控制台子系统）出现时才自己新建一个带窗口的控制台——主进程 `AllocConsole` 申请的隐藏控制台只能覆盖主进程自己的控制台子进程（taskkill 等），到不了引擎树。实验矩阵（真实 Electron 主进程 → 引擎 → runner → node.exe 叶子，各层打印自身 `GetConsoleWindow`/可见性）：A 主进程 AllocConsole+SW_HIDE、引擎按现状 `windowsHide: true` → 引擎与 runner 均无控制台，叶子新建可见控制台；B 去掉 `windowsHide` → 与 A 完全相同（**故「条件化 windowsHide」修不掉，原计划作废**）；C 主进程不申请控制台 → 同样弹窗；D 引擎改由控制台子系统 node.exe 启动 → 主进程/引擎/runner/叶子共享同一个隐藏控制台（hwnd 相同、`visible=false`）。回归来源：0.1.5-rc.1 新增 `dsh-subprocess-local` / `dsh-win32-process` / `dsh-sandbox-windows-acl`（旧 lock 均无此三包）；旧版每次派生自带 `windowsHide`（`CREATE_NO_WINDOW`）所以不弹窗，新版 runner 不带，且 ACL 受限子进程按上游设计不能用 `CREATE_NO_WINDOW` / `CREATE_NEW_CONSOLE`。可选路线：只能在青梧侧修——dsh 从终端启动时整条链本来就带控制台，上游复现不到这个问题。已排除：把隐藏控制台经 `NODE_OPTIONS=--require` 注入每个 node 子进程（开发期实测可行，但 Electron 明确禁止打包应用使用 `NODE_OPTIONS`，仅放行 `--max-http-header-size` / `--http-parser`，见官方 Environment Variables 文档，故打包后失效）；把引擎换成 electron.exe 之外的路径也不成立（GUI 子系统这一步就断了继承）。剩余两条：①内置一个控制台子系统的 node 运行时来启动引擎（实验 D 已验证：整链共享同一个隐藏控制台、零弹窗；代价是安装包 129MB → 约 +35–45MB，且该运行时需与 Electron 的 Node 版本对齐）；②主进程装 WinEvent 钩子（`EVENT_OBJECT_SHOW`），在引擎子孙的控制台窗口显示瞬间隐藏（零体积、不依赖上游，但窗口仍会被创建，极端情况可能看到极短闪烁，属绕机制手段）。验收：连续执行命令时不出现可见控制台窗口、不新增 conhost；走 ① 时另需确认打包态与开发态使用同一运行时
