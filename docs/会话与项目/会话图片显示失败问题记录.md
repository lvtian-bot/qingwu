# 会话图片显示失败问题记录

## 当前结论

- 修复状态：图片回读已按引擎新契约修正，事件折算保留整条图片引用；现行技术约束见 [会话与项目](会话与项目.md)。
- 根因：引擎 0.2.2-rc.1 起把 `session/attachment` 的入参由 `{ sessionId, attachmentId }` 改为 `{ sessionId, attachment }`（整条图片引用）。青梧自 v0.3.2 内置 0.2.2-rc.1，界面仍按旧参数请求，被引擎判为参数不合法，图片位置回退成灰块「图片加载失败」。
- 验证范围：以本机安装的 dsh 0.2.2-rc.2 的公开类型声明、typert 参数 schema，以及 npm 上 0.2.1-rc.3 与 0.2.2-rc.1 两个版本的实现对比为准；没有抓到该请求的实时报错——引擎不记录被拒绝的请求，界面也不显示错误码。
- 遗留事项：失败时界面只有「图片加载失败」，没有失败原因；同类问题再次出现时仍要靠附件落库情况与接口契约比对来定位。

## 2026-11-13：现象、根因与修复

### 现象

- 对话里用户发过的图片显示为灰块「图片加载失败」。刚发送的图片先显示本地预览，被引擎事件替换成正式气泡后变成灰块；排队栏缩略图只显示空占位。
- 影响范围：v0.3.2（2026-11-05，内置 dsh 0.2.2-rc.1）之后所有从会话记录回读的图片。AI 回复中的本地图片与右侧文件面板预览走主进程本地文件通道，不受影响。

### 证据

- 本机附件库中存在对应图片对象：39,063 字节、1266×392 的 PNG，写入时间就是发送时刻，说明上传、存储与模型读取都正常，问题只在界面回读。
- 引擎 0.2.2-rc.2 的 `SessionAttachmentRequest` 为 `{ sessionId, attachment: ImageAttachmentRef }`，参数 schema 把 `attachment` 标为必填；0.2.1-rc.3 及更早为 `{ sessionId, attachmentId }`。
- 引擎读取实现按引用逐项核对：媒体类型、字节数、宽高与存储内容不一致就判为附件损坏。
- 界面两处取图（消息区、排队栏）仍发送 `attachmentId`，事件折算也只保留了 ID、类型与宽高，丢掉了 `bytes`——即使改传整条引用也过不了字节数核对。

### 根因

- 引擎在 0.2.2-rc.1 把附件读取从「按会话授权、按 ID 取图」改成「按引用取图、由网关授权」，请求体结构随之变化。升级引擎时核对了会话列表、定时任务等端点，图片读取的请求体没有纳入契约测试：`tests/contract-installed-dsh.test.cjs` 只校验顶层参数名与返回类型，嵌套 `request` 的内部字段没有类型约束，测试仍然是绿的。

### 修复与验证

- 事件折算保留引擎给出的整条引用，界面按 `{ sessionId, attachment }` 请求，字节数随引用一起回传。
- 契约测试新增 `SessionAttachmentRequest` 的请求体断言（形状与字段双向覆盖），升级引擎时本地测试能直接发现契约漂移。
- `npm run check` 通过：类型检查、构建、单元测试与契约测试；实机发图依赖新版本验证。

### 教训

- 端点的「返回形状」有断言不等于「请求形状」有断言，两者都要纳入契约测试。
- 同类现象可能来自完全不同的链路：先确认附件是否已经落库，再判断是写入问题还是读取问题，不要直接套用上一次的根因。
