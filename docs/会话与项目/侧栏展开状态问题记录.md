### 系统性原因

1. **状态规则未统一。** 保存的收起偏好、搜索期间临时展开、当前会话所在项目临时展开、每组显示条数分别存在。标题、子列表与点击操作曾各自推导状态；最新提交统一了标题与列表，但当前项目的点击语义仍与注释矛盾。
2. **后置行为归属分散。** 新建成功后的展开写在置顶项目和普通项目两套按钮回调中，共用的 `createSessionIn` 及其其他调用入口没有同样行为。删除成功后清理也由行按钮发起，另外再用列表变化兜底，使责任分散。
3. **以列表内容推断加载阶段。** 曾直接把启动空列表视为删除后的列表；现用“曾见过非空列表”猜测基线就绪，仍不能准确表示空基线和删除最后一个项目。
4. **检查未覆盖新增交互。** PR 没有修改测试文件。`tests/sidebar-data.test.cjs` 主要覆盖排序、置顶、既有分区存储及源码结构，不执行新增项目折叠的状态转换、失败流程或多入口行为。150 项测试通过不代表这些交互经过验证；PR 描述也明确界面效果尚未人工验证。
5. **收尾记录早于实际验收。** TODO 已标完成，模块说明仍写“新建会话会先展开”，但代码已经改成成功后展开，且只覆盖项目行入口。记录未随审查结果完整更新。

### 最新 3 条意见的核对

#### 1. 新建会话入口不一致

- [审查意见](https://github.com/lvtian-bot/qingwu/pull/12#discussion_r4355751717)。
- 项目行新建成功后调用 `expandWorkspace`，清除保存的收起标记；顶部“新建会话”、首次发送、首次执行命令及切换项目落点调用共用的 `createSessionIn`，没有同样的展开后处理。
- 这些入口都能通过选中会话临时展开项目，差异在于离开该项目后是否恢复收起。按模块当前描述，入口不一致成立；实现前应明确“新建会话是否永久清除收起偏好”，避免仅为迎合意见进一步扩张行为。
- 建议在现有操作组合层统一成功后的策略，覆盖新建与复用空白会话，界面行只调用操作。无需新增后台机制。

#### 2. 长标题裁切箭头

- [审查意见](https://github.com/lvtian-bot/qingwu/pull/12#discussion_r4355751721)。
- 本次将 `.native-ws-title` 改为 `inline-flex`，标题仍是直接文本，箭头作为该元素内的 `::after`，而父元素保留 `overflow: hidden`。长标题存在把后面的箭头一并裁掉及省略号失效的布局问题。
- 静态结构支持该意见；本次未进行浏览器视觉复现，不将其记为人工界面验收结果。
- 建议让文字在独立可收缩子元素中省略，箭头独立占位，并验证长标题、窄侧栏及悬停按钮出现时的效果。

#### 3. 搜索时点击大分区改变保存偏好

- [审查意见](https://github.com/lvtian-bot/qingwu/pull/12#discussion_r4355751726)。
- 已用实际 `useSessionSidebar`、模拟 React Hook 调度和本地存储复现：搜索期间调用 `toggleSectionCollapse("projects")` 后，存储从空集合变为包含 `projects`，而显示层仍被搜索强制展开。清空搜索后才出现变化。
- 该逻辑在 PR 基准代码中已存在；本轮修复了项目层的同类问题，但没有覆盖“置顶 / 项目 / 会话”三大分区。
- 建议两个层级共用搜索期间不写入折叠偏好的规则，不能只修其中一个入口。

### 本次补充发现

#### 当前会话所在项目的标题点击无可见效果

- 已用实际 Hook 复现：保存记录为 `["w1"]`，当前会话属于 `w1`，项目呈现展开；点击标题后保存记录仍为 `["w1"]`，项目仍展开。
- 原因：`collapsedWorkspaceIds` 每次都会移除当前会话所属项目，标题点击即使写入收起标记也被立即覆盖。
- 模块说明的“当前会话所在项目保持展开”支持当前行为；但函数注释和第 2 轮回复声称“点击标题应真正收起”。这是行为约定冲突，不能直接以其中一方为准改代码。
- 待明确：当前会话所在项目必须始终展开，还是只在进入该项目时临时展开、随后允许手动收起。

#### 删除清理的兜底逻辑仍不完整，且收益需复核

- 已复现：非空项目列表变为空列表后，Effect 因 `workspaceIdSet.size === 0` 直接返回，最后一个项目的折叠记录保留。该现象针对流移除路径；从项目行删除成功仍会通过回调清理。
- “曾见过非空列表”不等于正式基线已加载，初始空基线也无法使其就绪。
- 注释称“移除推送先于删除回执会使成功回调漏清理”，但当前 Hook 生命周期由 `NativeApp` 持有，项目行移除本身并不阻止已注册 Promise 回调执行；该补充机制的必要性缺少代码证据。
- 这主要是低影响残留记录与维护复杂度问题，不应为了清理无效 ID 再引入复杂同步机制。先核对删除来源；需要处理流移除时，沿现有明确的 remove 事件或真实基线状态收尾。

### 后续处理建议与验收范围

1. 先明确当前项目是否允许手动收起，以及新建会话成功是否永久清除偏好；其他临时展开均不得自动改写保存记录。
2. 在现有模块内统一呈现判断及成功后的创建、删除处理，覆盖置顶和普通项目、顶部新建、首次发送、命令和项目切换；不新增引擎业务状态或后台同步模块。
3. 增加直接执行实际 Hook / 操作的回归验证：启动空列表到正式基线、搜索进入和退出及点击、当前项目切换、新建与复用空白会话、创建和删除失败、移除最后一个项目；对标题与子项一致性及长标题箭头做必要界面检查。
4. 处理本批全部意见后统一验证和推送；逐项记录修复、不采纳或延期结论，避免每条意见单独触发一轮审查。
